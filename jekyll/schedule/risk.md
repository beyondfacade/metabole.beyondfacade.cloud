# 위험 관리 방안

## 데이터·검증 위험

| 위험 | 현재 대응 | 남은 과제 |
|---|---|---|
| 작은 표본·값 누락 | 판정 가능한 신호 2개 미만은 보류 | 보류 비율·업종별 신뢰도 검증 |
| 업종마다 다른 판별력 | 업종별 백테스트 공개, 두 업종 제외 | 여러 기준 시점의 반복 검증 |
| 양도·양수·지연 신고 | 원천과 가정을 명시 | 인허가 폐업의 경제적 의미 검토 |
| 자료 공표 지연 | 기준 분기·산출일 구분 | 시점 누수·최신성 관리 |
| 유사 사례의 인과 오독 | 서울 전체 범위와 참고 해석 | 계절성·지원금·겹친 정책의 영향 |
| 뉴스 중복·질의 편향 | 같은 사건 접기, 평가셋 상태 구분 | 실제 사용자 질문·외부 평가셋 검증 |

## 서비스·운영 위험

LLM·타일·원천 API에 외부 의존이 있습니다. 자료별 실패 안내와 시연 캡처를 준비하되 완전 오프라인 동작을 약속하지 않습니다. 공개 배포에서는 쿠키·프록시 IP·OAuth·접근 제한·백업을 따로 검수합니다.

## 일정·표현 위험

10/23 프로젝트 마무리와 10/27 최종 발표 사이에는 발표 자료와 시연을 점검합니다. 팀장·풀스택 공동 개발 역할과 실제 서비스 주소는 사용자 확인을 반영했습니다. 목표를 실적으로, 브랜치 구현을 운영 배포로 바꾸지 않습니다. 현행 상태는 [일정]({{ '/docs/schedule/timeline.html' | relative_url }}), 검수 대기 항목은 [최종 검수]({{ '/docs/deliverables/final-inspection.html' | relative_url }})에 모읍니다.
